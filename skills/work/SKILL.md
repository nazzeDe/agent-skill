# 测试驱动实现与静态门禁校验（Work）

基于 skeleton 阶段的架构设计，在同一阶段内完成：签名补全、契约测试编写、业务逻辑实现，并通过全部静态门禁。

**核心理念**：测试与实现同步演进，在编译器与测试的双重约束下逐步达到可工作状态。

## 第一步：接收 Skeleton 设计并补全签名

接收 skeleton 返回的设计摘要作为输入：
- **设计声明**：模块定位/修改点选择
- **数据结构设计**：类型定义
- **接口签名清单**：函数签名 + 职责说明 + 实现提示
- **模块交互关系**：调用关系与数据流

**补全签名到可编译状态**：
* 将 skeleton 设计中的类型定义与函数签名**真正写入源码**
* 为函数体添加 `todo!()` / `raise NotImplementedError` / `throw new Error("todo")` 占位
* 确保代码结构能够编译（类型定义正确、导入路径正确、函数签名语法正确）
* **签名缺陷上报**：若发现 skeleton 设计的签名无法表达实现需求、类型定义缺失关键字段，**立即停止**并报告具体缺陷，要求回到 skeleton 阶段修正。
* **完成判据**：类型定义与函数签名已写入源码，代码结构能够编译（即使函数体是 `todo!()`）。**这是中间态，不是交付态**——交付判据在第四步（占位归零 + DoD 真跑）。

## 第二步：编写契约测试（Test-First）

以 **"少即是多（Less is More）"** 与 **"测试即契约"** 为准则，编写高密度测试。

### 确定测试靶点（Macro Seam & Micro Fault-Isolation）

基于 skeleton 的**接口签名清单**与**模块交互关系**，确定测试覆盖范围：

* **宏观公共入口（Public Seam Contract）**：在模块对外暴露的公共接口上编写测试，使读者仅读测试即可理解该模块的输入输出契约与边界行为。
* **微观非平庸转换节点（Micro Fault-Isolation Tests）**：对内部承担独立算法、复杂分支或核心数据变换的子函数，编写轻量输入输出测试。当系统出错时，这些测试可直接在调用链上进行二分故障隔离（Binary Fault Isolation），避免全链路黑盒调试。
* **跳过平庸函数**：无实质逻辑的代码（简单数据组装、参数原样转发、getter/setter）不写测试。
* **完成判据**：每个测试靶点均具有明确的接口契约描述价值或二分故障隔离价值。

### 编写高密度失败测试（Red）

编写测试代码并遵守以下准则：
* **基于设计意图编写测试**：参考 skeleton 的**职责说明**与**实现提示**，理解函数的输入输出契约、前置条件、后置条件。
* **表驱动优先（Table-Driven）**：同一函数若有多个输入输出边界，合并为一张紧凑的输入输出映射表，严禁复制粘贴多个结构雷同的测试函数。
* **独立字面量断言（Literal Assertions）**：期望值必须使用独立已知的字面量或具体样本，严禁在测试中将待测实现逻辑重写一遍来计算期望值（Tautological Test）。
* **严禁四类低价值测试**：
  * **不测平庸透传（Trivial Pass-Through）**：无实质逻辑的代码不写测试。
  * **不与静态类型重复（Type-Redundant）**：静态类型系统已保证不可能发生的非法输入，不写运行时测试。
  * **不写耦合实现的交互 Mock（Implementation-Coupled Mocks）**：严禁 Mock 内部协作者并断言调用顺序；仅验证接口的输入与可观测输出。
  * **不写等价类冗余枚举（Redundant Enumeration）**：同一等价类仅保留边界代表，剔除无信息增量的枚举样本。
* **验证预期失败（Red Verification）**：运行测试命令，确认所有新增测试均通过编译，且**因预期的业务逻辑尚未实现（如触发 `todo!()` 或断言失败）而失败**，而非因语法、类型或导入错误而失败。
* **完成判据**：新测试全部通过编译，且因预期业务未实现而失败（Red）。

## 第三步：编写最小实现（Green）

* **遵循签名不可变性**：严格在已锁定的公共类型定义与函数签名内部编写函数体实现。**严禁私自修改跨模块公共类型、结构体字段或函数签名**（在多 Worktree 并行执行时防止跨模块契约冲突）。
* **最小实现原则**：仅编写使契约测试与故障隔离测试通过（Green）所需的最小逻辑。优先使用标准库组合子与纯函数变换，避免手写带可变游标的命令式循环状态机。
* **范围纪律与注释精简（Scope & Comment Discipline）**：
  * 严禁添加需求未要求的配置项、防御性分支、未被调用的辅助函数或未请求的 UI 元素。
  * 严禁残留任何分步解说式注释（如 `// Step 1`）、被注释掉的死代码或复述函数签名的文档注释；若确需保留注释，必须同时满足注释三项判据（引入代码字面之外的信息、删掉会破坏不变量、能否压缩为极简一行）。
* **临时调试代码清理（Debug Artifact Cleanup）**：若实现过程中添加了临时打印语句或仅验证内部步骤的临时测试，在测试通过后立即删除。
* **完成判据**：业务功能已实现，所有测试通过（Green），无任何范围外附加逻辑或冗余注释。

## 第四步：静态门禁校验与修复循环（Static Gate Loop）

实现完成后，立即执行项目的确定性静态门禁：
* **优先执行项目门禁脚本**：若存在 `./scripts/gate`（或 `AGENTS.md` 中声明的 Static gate 命令），直接运行该脚本。
* **默认回退门禁序列**（当项目尚未运行 `/init-project` 生成 `./scripts/gate` 时，依次运行）：
  * 编译与类型检查 + 项目 Linter（将 warnings 视为 errors）；
  * 全量测试套件；
  * 纯圈复杂度检查：`/home/nazze/Studio/oss/unclebob/crapper/crapper --no-coverage --changed --threshold 10`；
  * 结构重复度检查：`/home/nazze/Studio/oss/unclebob/dryer/dryer`。
* **迭代修复**：
  * 若圈复杂度超标（`CC > 10`）：通过化简条件分支、利用上游调用契约删除多余防御判断或提取内聚纯函数来降低复杂度。
  * 若结构重复度超标（`>= 0.8`）：抽取共享变换逻辑（包含测试代码中的重复 Setup），确保同一逻辑仅在一处定义。
  * 每次修改后重新运行完整静态门禁，直至退出码为 `0`。
* **占位零残留**：本次变更内 `todo!()` / `unimplemented!()` 计数必须为 `0`。静态门禁通过但占位仍在，等于没实现。
* **DoD 真跑一次**：完成定义必须经过一次真实运行验证（起进程 / 建连接 / 发信号），不能用编译结果或单测代替。
* **完成判据**：静态门禁命令完整跑通且退出码为 `0`，且上述两条成立。

* **完成判据**：所有低信噪比测试已被剔除，剩余测试兼具最小体积与完整的故障隔离定位能力。
