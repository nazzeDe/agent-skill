# AI 编程工作流设计原则：分阶段规约精化与函数式管道

## 第一性原理：从欠定需求到完备实现的分步精化（Stepwise Specification Refinement）

自然语言业务需求通常是**欠定的（Under-specified，信息量低、歧义度高）**；而生产级代码必须**完全确定（Fully Specified，零歧义、类型与边界自洽）**。

大模型生成代码的过程，本质上是根据上下文分布补全需求中未显式定义的中间信息（数据结构、边界状态、调用契约、局部实现）。

由此推导出核心准则：
* **单步端到端生成必然引入偏差**：从原始自然语言需求一次性直接生成最终代码，迫使模型在巨大的解空间中同时推断所有未定义维度。每一层决策的微小偏差会在长链路上逐级放大，产生两类系统性问题：
  * **语义偏差（Semantic Drift）**：实现行为偏离真实业务意图；
  * **结构退化（Structural Degradation）**：倾向于在下游报错点叠加防御性分支与局部补丁（Additive Patching），破坏系统原有的简洁性与一致性。
* **工作流的核心目标是“规约保真（Specification Fidelity）”**：将不确定的端到端代码生成拆解为**信息逐级具体化、每步可独立验证的精化管道**。

## 核心范式：函数式管道与分阶段转换

将端到端代码生成分解为状态可观测、单步职责单一的函数式复合变换：

$$Code_{final} = (f_{refine} \circ f_{work} \circ f_{contract} \circ f_{skeleton})(Intent)$$

### 状态演进的基准阶段
每一阶段转换仅引入**单一维度**的工程决策，禁止跨阶段跳跃：

* **意图对齐（`align` / Intent & Alignment）**：将模糊的自然语言需求或缺陷表象收敛为无歧义的需求契约。
  * **退出门禁（需求歧义审查 / `Ambiguity Gate`）**：主持对话的 Agent 容易因共享上下文而忽略隐式假设。对齐结束前，必须由无对话背景的独立 Fresh-Context Agent 对需求契约执行严格字面审查（检查是否存在多重合法字面解释、未定义的异常状态或未划定的非目标范围），仅当输出 `PASS` 时才算完成对齐。
* **静态类型与接口签名（`skeleton` / Types & Signatures）**：消除结构歧义，锁定系统的静态类型与模块边界。
  * **核心产物**：领域统一术语（Canonical Terms）、核心数据结构（Data Shape / Types）、跨模块接口签名（Seams / Function Signatures）、上游调用方不变量（Caller Invariants）。
  * **核心原则**：先定义数据结构，再编写逻辑；利用类型系统使非法状态在编译期不可表示（Make illegal states unrepresentable）；先向上游回溯定位最小根因修改点，再决定修改位置。
* **行为契约与故障隔离测试（`contract` / Contract & Fault-Isolation Tests）**：消除边界歧义，锁定各层关键接口的可观测行为。
  * **核心产物**：基于已锁定的接口签名，在公共接口（Public Seam）与内部非平庸转换节点上，编写高信息密度的预期失败测试（Failing Tests / Red）。
* **最小可行实现（`work` / Minimal Implementation & Static Gate）**：在不修改已锁定公共签名的前提下编写最小函数体实现，并通过全部确定性静态检查。
* **多维审查与代码化简（`refine` / Multi-Agent Review & Simplification）**：在不改变外部可观测行为的前提下，消除下游冗余补丁、降低圈复杂度、消除结构重复、对齐代码品味与注释规范。

### 动态切入（按初始需求明确度选择入口）
任务从哪一阶段切入，取决于初始输入的明确程度：
* 模糊新特性：从 `align -> skeleton -> contract -> work -> refine` 完整执行。
* 边界明确的功能或需定位根因的缺陷：直接从 `skeleton`（定义签名）或 `contract`（编写测试）切入。
* 修改点与签名已固定的局部修改：直接从 `work -> refine` 切入。

### 验证与审查的三级过滤（Static $\to$ Agent $\to$ Human）
所有实现与验证遵循**“确定性静态工具拦截机械错误 $\to$ 独立 Agent 审查语义与结构 $\to$ 人类仅确认业务意图与最终结果”**：
* **静态工具层（Static Gate）**：拦截一切可确定性计算的错误（语法、类型、Linter、测试执行、圈复杂度、AST 结构重复度）。
* **独立审查 Agent 层（Orthogonal Reviewers）**：静态工具无法判定的“修改位置是否处于最优上游、测试是否精炼且具备故障隔离力、代码是否符合项目品味”，由职责正交的独立 Agent 完成审查与重构闭环。
* **人类决策层（Human-in-the-Loop）**：人类仅介入**源头业务意图对齐（`align`）**、**接口签名确认（`skeleton` Checkpoint）**以及审阅通过全部门禁后的**最终变更**。

## 静态工具与 AI 的职责边界

> **凡是确定性静态工具能判定的事项，一律由静态工具拦截；AI 仅负责静态工具无法判定的语义规约、架构边界与代码表达。**

* **静态工具作为阶段退出的硬门禁（Static Hard Gate）**
  以下检查是 `work` 阶段得以退出的**前置条件**：
  * 语法、类型检查与 Linter；
  * 全量测试套件通过；
  * 纯圈复杂度上限（不绑定行覆盖率指标，防止为凑覆盖率而生成无价值测试）；
  * AST 级结构重复度检测。
  * **拦截机制**：任一指标未通过，由静态门禁脚本直接返回非零退出码并在 `work` 阶段内部修复，严禁流入 `refine` 审查阶段或交付给人类。

* **规则向底层工具沉淀的闭环**
  审查与复盘中总结出的规则，按可确定性程度持续向底层工具转化：
  `人工代码修改` $\xrightarrow{\text{提炼}}$ `代码品味条目（taste.md）` $\xrightarrow{\text{形式化}}$ `静态 AST / Lint 规则（./scripts/gate）`。

## 测试原则：少即是多，测试即契约

生成测试代码的低成本容易导致**测试膨胀（Test Bloat）**：为了追求表面覆盖率而生成大量耦合实现细节、难以维护的低信噪比测试。

工作流对测试遵循 **“少即是多（Less is More）”** 与 **“接口即契约，测试即文档”** 原则：

### 测试存在的两类价值
判断一个测试是否应当存在，取决于其**契约描述价值**与**故障隔离价值**：
* **公共接口契约（Public Seam Contract）**：在模块对外暴露的公共接口上编写测试，清晰定义该接口承诺的输入输出变换与边界行为。
* **微观故障隔离测试（Micro Fault-Isolation Tests）**：在复杂调用链（$F = f_c \circ f_b \circ f_a$）中，针对内部承担独立算法或复杂数据变换的子函数编写轻量输入输出测试。当顶层测试失败时，微观测试可直接将故障隔离到具体子函数，避免全链路黑盒排查。

### 必须剔除的四类低价值测试
* **平庸透传测试（Trivial Pass-Through）**：被测代码无实质逻辑（如简单数据组装、参数原样转发、getter/setter）。
* **与静态类型重复的测试（Type-Redundant）**：静态类型系统与编译器已保证不可能发生的非法状态，不写运行时测试。
* **耦合实现的交互 Mock 测试（Implementation-Coupled Mocks）**：通过重度 Mock 内部协作者来断言“先调用 A 再调用 B”，将内部实现步骤重复抄写一遍，重构时极易断裂。
* **等价类冗余枚举（Redundant Enumeration）**：同一等价类或代码路径下复制粘贴出多个结构相同的测试函数；必须合并为紧凑的表驱动测试（Table-Driven）或仅保留边界代表。

### 测试信噪比的三级过滤
* **静态工具层**：执行测试套件，并通过 AST 结构查重工具（`dryer`）拦截复制粘贴的测试代码。
* **独立 Test SNR Reviewer Agent**：在交付前对测试集执行双向审查：
  * **删减冗余**：剔除上述四类低价值测试，将零散同构测试合并为表驱动测试。
  * **补齐故障隔离点**：对照调用链上的复杂内部转换节点，检查是否具备足够的微观故障隔离测试。

## 信噪比准则：范围纪律与信息精简

工作流中每一行新增的代码、UI 元素、注释与文档，都必须直接服务于已确认的需求契约。

### 代码与 UI 的范围纪律（Scope Discipline / No Unrequested Additions）
* **禁止范围外扩写**：任何不在需求契约内的附加内容——包括代码中为假想未来预留的配置项、未被调用的辅助方法、违反调用方不变量的防御性分支，以及 UI 中未经要求的副标题、装饰性文案、多余按钮或交互状态——一律视为范围蔓延（Scope Creep）。
* **删减判据**：移除该 UI 元素或代码分支后，当前锁定的需求契约是否依然成立？若依然成立，必须直接删除。

### 注释精简准则（Comment Only the Unexpressed）
* **代码自解释 WHAT 与 HOW**：凡是能通过类型签名、标识符命名与函数拆分直接表达的逻辑，严禁添加注释。
* **保留注释的三项判据**：
  * **删掉它，调用者或维护者是否会破坏隐藏的不变量或前置条件？**
  * **是否引入了代码字面之外的信息？**（如外部协议限制、硬件边界、缺陷编号、反直觉实现背后的性能或兼容性权衡）
  * **能否压缩为极简的一行？**
  * 不满足以上全部条件的注释（尤其是分步解说注释与复述参数名的样板文档注释）一律删除；同时在静态 Linter 中关闭强制要求所有函数/类编写文档注释的规则。

### 文档最小化准则（Codebase as Single Source of Truth）
* **禁止复述代码现状的说明性文档**：目录结构、类型定义与契约测试本身即为准确的实时文档。严禁生成总结“模块包含哪些文件、接口如何调用”的说明性文档（此类文档随代码演进会迅速过期失真）。
* **仅记录代码无法直接表达的元决策**：仅维护两类极简文档——**领域术语表与架构决策记录（`GLOSSARY.md` 与 `docs/adr/`，记录为什么排除其他方案）**，以及**代码品味库（`docs/agents/taste.md`）**。

## 复杂度控制与正交职责审查（Orthogonal Multi-Agent Review）

大模型在修改代码时普遍存在**局部补丁偏好（Additive Patching Bias）**——倾向于在下游报错点添加防御性判断与状态标志，而非修正上游前提假设或数据结构。同时，单个 Agent 在同一上下文内同时兼顾多项审查维度时，容易产生注意力分散。因此，复杂度控制采用以下双阶段与分权审查机制：

### 双阶段防止代码膨胀
* **前置定位上游修改点（`skeleton` 阶段）**：顺着数据流向上游回溯——问题源于生产端还是消费端？上游调用契约已保证了哪些不变量？能否通过修改一处数据结构或入口归一化直接消除下游分支？
* **后置代码化简（`refine` 阶段）**：在实现阶段跑通测试与静态门禁后，由无历史上下文负担的独立审查 Agent 基于完整 Diff 执行代码减法与上移重构。

### 职责正交的独立审查管道（`refine`）
进入 `refine` 阶段的代码已通过全部静态门禁。审查拆分为**职责单一、视角正交、拥有独立全新上下文（Fresh Context）**的四个审查角色，按严格优先级裁决（第一阶段拥有一票否决权）：

* **根因与代码减法审查（`Subtraction Reviewer`）**
  * **职责**：宏观审视修改位置与代码体积。检查是否存在下游局部补丁、违反调用方契约的冗余防御判断、未经请求的范围扩写或冗余文档。
  * **裁决顺序**：最先串行执行。若修改位置错误或存在冗余补丁，直接打回重构；在代码化简完成前，不启动后续微观审查。
* **测试信噪比与故障隔离审查（`Test SNR Reviewer`）**
  * **职责**：剔除平庸透传测试、类型重复测试与耦合实现的交互 Mock 测试，将同构枚举测试压缩为表驱动；同时验证复杂内部转换节点是否具备故障隔离测试。
* **规约保真审查（`Spec Fidelity Reviewer`）**
  * **职责**：核对外部行为契约。检查是否存在需求遗漏、逻辑偏差，或通过削弱测试断言/编写恒真断言（Tautological Assertions）使测试失效的行为。
* **代码品味与注释审查（`Taste & Comment Reviewer`）**
  * **职责**：微观模式匹配与注释清理。对照 `docs/agents/taste.md`（`when -> instead -> why`）与注释规范，消除命令式手写游标循环、分散的状态变更、局部代码坏味道及所有不满足三项判据的冗余注释。

### 审查输出准则（Silence on Pass）
任何审查角色禁止输出模棱两可的建议性评论。每一条拦截必须附带明确证据（上游调用点位置、违背的具体契约条款或命中的具体品味/注释规则）；若无明确违规项，唯一合法输出为 `PASS`。

## 并行执行原则：串行定义契约，并行编写实现（Skeleton-First MapReduce）

在多 Agent 并行开发时，若直接按业务切片各自独立设计数据结构与接口，极易在合并时产生跨模块类型冲突与重复逻辑。

兼顾**全局架构一致性**与**并行吞吐效率**的执行方式是 **“串行定义契约，并行编写实现”**：

* **串行统一设计（Types & Signatures / Reduce Design）**
  **跨模块数据结构与接口契约必须由单一主节点在源头统一定义。**
  在 `skeleton` 阶段，由单个高推理能力模型统一设计**类型定义、数据结构与函数签名清单**，以设计摘要返回主控、**不改动仓库任何文件**（结束时 `git status` 干净），经人类确认后原样转发给 `work` 落盘。
* **并行独立实现（Implementation / Map Execution）**
  只有在类型与签名契约被设计摘要锁定并经人类确认后，才按**无共享状态的正交模块/函数边界**分发给多个并行工作节点（Worktrees）。
  * **执行准则**：并行节点仅在已锁定的函数签名内部编写实现与测试，**严禁私自修改跨模块公共类型与接口签名**。若发现接口签名本身无法满足需求，必须中断并上报主控节点统一修正。
* **合流校验与全局去重（Reduce Verification）**
  除多模块实现外，**前置代码库检索（多路 `scout` 并行）**与**后置多维审查（三路 `reviewer` 并行）**全面并行化。所有并行实现分支合并后，在全局 Diff 上统一运行静态门禁（`./scripts/gate`，含 `dryer` AST 查重）与 `Subtraction Reviewer`，消除各分支内部各自产生的重复局部逻辑。
