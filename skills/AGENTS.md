# AI 编程工作流设计哲学：渐进保真与函数式扩写

## 第一性原理：代码生成即“超分辨率重建”

人类给出的业务需求，本质上是一张**低像素图片（低信息量、高信息熵）**；而生产级代码是一张**高分辨率工程图纸（信息完备、零歧义、与系统全局自洽）**。

大模型写代码的过程，本质上是根据上下文概率分布，去填补需求中原本不存在的大量中间信息（数据形状、边界异常、调用契约、局部写法）。

由此推导出核心铁律：
* **一步跨越必然失真**：从原始需求直接生成最终代码，等于让模型在巨大的解空间中一次性脑补所有维度的缺失信息。每一层决策的微小偏移会在长链路上指数级放大，最终产生两种必然的失真：
  * **语义失真**：扩写出的内容偏离真实需求；
  * **风格与结构失真**：通过防御性堆砌与增量打补丁（如用两百行补丁解决两行根因问题），破坏系统原有的简洁性与一致性。
* **工作流的唯一使命是“保真”**：AI 工作流不是为了提升“单次生成代码的数量”，而是建立一条**信息逐步降熵、步步可校验的扩写管道**。只要初始需求正确，管道就能以最高确定性收敛到生产级代码。

## 核心范式：函数式管道与小步上采样

将模糊的、端到端不确定的代码生成，拆解为状态可观测、单步跨度极小的函数式复合变换：

$$Code_{final} = (f_{refine} \circ f_{work} \circ f_{contract} \circ f_{skeleton})(Intent)$$

### 状态演进的基准阶梯
每一阶变换只允许注入**单一维度**的信息，严禁跨阶脑补：

* **原始意图与对齐（Intent & Alignment）**：将模糊的自然语言需求或缺陷表象收敛为无歧义的意图契约。
  * **退出门禁（抗曲解测试 / Ambiguity Gate）**：主持对话的 Agent 极易因“共享上下文幻觉”而放过隐式假设。对齐结束前，必须由毫无对话背景的独立 Fresh-Context Agent 对需求契约执行“恶意曲解测试”（检查是否存在多种合法字面解释、未定义的异常黑洞或未划定的防镀金边界），仅当输出 `PASS` 时才算真正对齐。
* **领域与静态骨架（Skeleton）**：消除语义歧义，锁死系统的静态结构。
  * **扩写内容**：领域统一词汇、核心数据结构（Data Shape / Types）、跨模块接口签名（Seams）、上游调用契约与不变量（Invariants）。
  * **核心原则**：先定数据形状，再谈逻辑；用类型系统让非法状态不可表示；先找上游根因支点，再决定修改位置。
* **行为契约（Contract / 接口即测试）**：消除边界歧义，锁死各层关键接口的可观测行为。
  * **扩写内容**：基于已锁定的接口签名，在宏观业务入口与关键微观转换节点上，编写高信息密度的可执行失败测试（Red）。
* **最小可行实现（Make it Work）**：消除实现幻觉，求得首个可行解。
  * **扩写内容**：填充使测试通过的最小代码修改。
* **代数化简与品味提纯（Make it Right）**：消除工程熵增与风格失真，收敛至生产级代码。
  * **扩写内容**：在不改变外部行为的前提下，消除结构重复、降低复杂度、剔除冗余防御代码、对齐代码品味。

### 动态切入（按“原图清晰度”短路）
上述阶梯是完整状态机的标准接口，而非僵化的教条流程。任务从哪一阶切入，取决于初始输入的“分辨率”：
* 模糊新特性：从 `原始意图 -> 静态骨架 -> 行为契约 -> 最小实现 -> 品味提纯` 完整流转。
* 边界明确的小功能：直接从 `静态骨架`（锁签名）或 `行为契约`（写测试）切入。
* 根因已知的局部重构：直接从 `最小实现 -> 品味提纯` 切入。

### 算力与认知的三级过滤（Static $\to$ Agent $\to$ Human）
所有工作与验证严格遵循**“静态工具兜底确定性 $\to$ Agent 穷尽语义与结构把关 $\to$ 人类只做高维意图拍板”**：
* **静态工具层（零认知成本）**：拦截一切可计算的错误（语法、类型、测试执行、圈复杂度、结构重复）。
* **专职 Agent 层（替代人类机械审阅）**：静态工具做不到的“支点是否选错、测试是否精炼够用、代码是否符合品味”，必须先由独立视角的 Agent 完成过滤、压缩与重构。**绝不允许把未经 Agent 提纯的毛坯代码或膨胀测试直接甩给人类。**
* **人类裁决层（仅做意图拍板）**：人类只处理连 Agent 都无法替你拍板的**源头业务意图对齐**，以及审阅最后被静态工具和 Agent 反复挤压干水分后的**极简最终产物**。

## 算力铁律：静态工具与 AI 的绝对边界

> **凡是确定性静态工具能判定的事，一律禁止消耗 AI 注意力；AI 只负责静态工具无法触及的语义、架构支点与代码品味。**

* **静态工具焊死为“阶段退出门禁（Hard Gate）”**
  以下检查不属于“代码审查（Review）”，而是实现阶段得以退出的**物理前提**：
  * 语法、类型检查与 Linter；
  * 全量测试通过；
  * 纯圈复杂度上限（剔除覆盖率捆绑，防止 AI 为刷覆盖率分母而制造垃圾测试）；
  * AST 级结构重复度检测。
  * **拦截机制**：任一指标未达标，由确定性脚本直接拦截打回，绝不流转至下一阶段，也绝不交给人类或 Review AI 过目。

* **知识的单向下沉飞轮**
  人类与 AI 在高阶审查中沉淀出的经验，按确定性程度持续向底层下沉：
  `人类的直觉修改` $\xrightarrow{\text{提炼}}$ `成文的代码品味（Taste 条目）` $\xrightarrow{\text{形式化}}$ `静态 AST / Lint 规则`。

## 测试哲学：少即是多，测试即程序

在 AI 时代，生成测试代码的边际成本趋近于零，这导致了全新的工程灾难：**AI 会为了写测试而写测试、为了凑覆盖率而写测试，用海量低价值测试淹没人类的审查与维护精力。**

测试覆盖率只能提供虚假的信心。本工作流对测试秉持 **“少即是多（Less is More）”** 与 **“接口即程序，测试即程序”** 的核心理念：

### 测试存在的正当价值
判断一个测试是否应该存在，**不取决于它测的是顶层接口还是底层小函数，而取决于它的信息密度与诊断价值**：
* **契约即程序（描述价值）**：好的测试本身就是程序最清晰的说明书。无论是宏观业务入口，还是内部承担独立非平庸转换的微观函数（$F = f_c \circ f_b \circ f_a$ 中的每一个关键子函数），其测试应当让人一眼看懂“该接口承诺了什么输入输出变换”。
* **故障二分探针（排错价值）**：在复杂链路中，针对关键底层子模块/纯函数的小测试是故障定位的锚点。当系统出错时，小测试能瞬间将排错半径锁定在具体节点，避免在顶层黑盒测试失败后进行高成本的全链路排查。

### 必须无情剔除的“垃圾测试”
* **平庸透传测试**：被测代码无实质逻辑（如简单的数据组装、参数透传、getter/setter），测它纯属噪音。
* **与类型系统重复的测试**：静态类型与编译器已经保证不可能发生的非法状态，严禁再写运行时测试。
* **复读机式脆弱测试**：通过重度 Mock 内部协作者来断言“先调了 A 再调了 B”，把实现步骤用测试语法抄了一遍，毫无契约价值且一重构就碎。
* **低密度枚举膨胀**：同一等价类或代码路径下，复制粘贴出大量相似测试函数。必须将其坍缩为紧凑的数据驱动表（Table-Driven）或少量边界代表。

### 测试的三级过滤治理
判断“测试够不够、精不精”，同样遵循 **静态工具 $\to$ 专职测试审查 Agent $\to$ 人类** 的漏斗，不消耗人类精力去筛查测试代码：
* **静态工具筛底线**：负责跑通测试、通过 AST 查重工具拦截复制粘贴的测试样板、并在核心纯逻辑模块按需运行靶向变异测试（验证断言是否真的锁死了核心分支，而非只刷行覆盖率）。
* **专职 Test Reviewer Agent 筛信噪比**：在交付给人之前，由独立的测试审查 Agent 对测试集执行双向洗礼：
  * **砍冗余（精不精）**：识别并直接打回上述垃圾测试，将零散的同构测试压缩为高密度的表驱动测试。
  * **补探针（够不够）**：对照调用链上的非平庸转换节点，检查一旦顶层出错，当前测试集是否足以在二分排查中瞬间定位故障节点。
* **人类免于排雷**：经过前两级洗礼后，测试本身已经极度精炼，人类无需在垃圾测试堆里肉眼排雷。

## 信噪比铁律：反衍生噪音与信息极简主义

在生成成本趋近于零的背景下，AI 有极强的倾向通过“附赠额外内容”来表现积极性，从而引发严重的**信噪比崩塌**。工作流必须遵循**“零衍生噪音原则”——每一行新增的代码、UI 元素、注释与文档，都必须证明其不可替代性，否则一律视为有害负债。**

### 代码与 UI 的零镀金原则（No Unasked Garnish）
* **未经请求皆为失真**：任何不在需求契约内的“贴心扩写”——包括代码中为假想未来预留的配置项、未被调用的辅助方法、防御不可能状态的兜底分支，以及 UI 中未经要求的副标题、装饰性文案、多余按钮或假想的交互状态——本质上都是**污染系统的噪音**。
* **删减判据**：拿掉这个 UI 元素或这行代码，当前锁定的需求契约是否依然成立？若依然成立，必须无条件删除。

### 反解说式注释（Comment Only the Unexpressed）
AI 极易将辅助自身推理的“思维脚手架”（如 `// 第一步：解析参数`、`// 遍历列表并过滤`）遗留在源码中，形成解说式垃圾注释。
* **代码自解释 WHAT 与 HOW**：凡是能通过类型签名、变量命名与函数拆分看懂的逻辑，严禁配任何注释。
* **注释存活的唯一判据**：
  * **删掉它，读者是否会踩坑做错事？**（承载隐藏的不变量或前置条件）
  * **是否引入了代码字面之外的词？**（如外部协议限制、硬件边界、上游缺陷编号、反直觉实现背后的取舍依据）
  * **能否压缩为极简的一行？**
  * 不满足以上条件的注释（尤其是复述参数名与函数名的样板 Docstring），一律剔除；同时在静态 Linter 中彻底关闭强制要求所有函数/类编写文档注释的规则。

### 反腐烂文档（Codebase as Single Source of Truth）
人类不想看、也不会去维护任何复述代码现状的文档。
* **禁止为代码做自然语言缓存**：目录结构、类型骨架与契约测试本身就是永远不会过时的活文档。严禁生成任何总结“模块包含哪些文件、接口如何使用、流程如何调用”的说明性文档——这类文档在写完的下一秒就会随着代码演进而腐烂，成为误导后续开发的沉积层（Sediment）。
* **仅记录代码无法表达的“元决策”**：工作流只允许沉淀两类极简文本——**统一的领域词汇与架构取舍依据（记录为什么排除其他方案，而非描述当前方案长什么样）**，以及**成文的代码品味（Taste 条目）**。

## 对抗熵增：双阶段防膨胀与分权审查（Review 哲学）

AI 生成代码最大的工程顽疾是**“局部增量补丁偏好（Additive Patching Bias）”**——倾向于在下游报错点堆砌防御性判断与状态胶水，而非修正上游前提假设或数据形状。

同时，单一 AI 在同一上下文内兼顾多项审查指标时，必然发生**注意力漂移**与**满足性偏差（抓到几个小问题即草草交差）**。因此，控制复杂度与保证品味必须遵循以下机制：

### 双阶段对抗代码膨胀
* **事前找支点（前置预防）**：在静态骨架阶段，强制沿数据流向上游回溯——问题出在消费端还是生产端？上游调用契约已经保证了哪些不变量？能否通过修改一处数据结构或入口归一化直接消灭下游分支？
* **事后做坍缩（代数约分）**：允许实现阶段先用笨办法跑通测试（将所有隐藏边界暴露在具象代码中），随后在提纯阶段由完全无历史包袱的独立上下文，基于“已知可行解”做纯粹的代码减法与上移重构。

### 正交分权与优先级审查（Multi-Agent Orthogonal Review）
进入 Review 阶段的代码已通过全部静态门禁。Review 阶段必须拆分为**职责单一、视角互斥、拥有全新上下文**的独立审查角色，并按严格优先级自上而下裁决（前序角色拥有一票否决权）：

* **根因与减法审查（Subtraction & First-Principles）**
  * **唯一视角**：宏观审视修改支点与体积。质询“如果项目最初就有此需求，代码也会这样写吗？”、“是否在下游打补丁？”、“能否通过调整上游契约或使用组合子砍掉绝大部分增量代码？”
  * **裁决位置**：位于最上游。若架构支点错误，直接打回重做；在臃肿补丁未压缩为极简修改之前，进入后续审查毫无意义。
* **测试信噪比与故障定位力审查（Test Signal-to-Noise & Pinpointing）**
  * **唯一视角**：专职审视测试的“少即是多”。负责砍掉平庸透传测试、类型重复测试与复读机 Mock 测试，将枚举噪音压缩为表驱动；同时验证关键转换节点是否具备故障二分定位探针。
* **规约保真审查（Spec Fidelity）**
  * **唯一视角**：核对外部行为契约。检查是否存在需求遗漏、越界扩写（Scope Creep），或通过篡改/削弱测试断言来蒙混过关。
* **代码品味与降噪审查（Taste & Noise Alignment）**
  * **唯一视角**：微观模式匹配与噪音剃除。严格对照沉淀的品味库（`when -> instead -> why`）与注释规范，消除手写低级循环、摊大饼式状态协作、违反调用点契约的无价值防御代码，以及所有解说式垃圾注释、未经授权的 UI 缀饰与冗余文档。

### 审查静默原则（Silence on Pass）
任何审查角色严禁输出“建议考虑”、“或许可以”等凑数评论。每一条拦截必须绑定确凿证据（上游调用点位置、违背的具体规约或命中的具体品味条目）；无实锤硬伤即输出 `PASS`。所有拦截在内部闭环消化，仅在全部 `PASS` 后向人类交付最终极简结果。

## 并行哲学：集权锁骨，放权填肉（Skeleton-First MapReduce）

传统的“按业务纵向切片（Vertical Slices）+ 自然语言工单”在多 AI 并行时会引发灾难：多个并行的 AI 为各自工单寻找局部最优解，各自发明数据结构与辅助逻辑，最终合并出冗余割裂的“架构缝合怪”。

要在保证**全局架构最优**的前提下榨干**并行效率**，必须遵循 **“集权锁骨，放权填肉”**：

* **串行集权（锁骨 / Reduce Design）**
  **全局最优解无法由并发节点民主协商产生，必须由单一主脑在源头锁死。**
  在骨架阶段，由单个高推理能力模型统一设计并直接在代码库中落盘**真实的类型定义、数据结构与空函数签名骨架**（而非自然语言描述的文档）。
* **并行放权（填肉 / Map Execution）**
  只有在代码级接口签名与类型契约被静态锁死后，才按**正交的模块/函数边界**分发给多个并行工作节点（Worktrees）。
  * **执行铁律**：并行节点只准在锁定的签名内部填充实现与测试，**严禁私自修改跨模块公共类型与契约**。若发现骨架本身无法满足需求，必须中断并上交主脑统一修正骨架。
* **全局合流与统一坍缩（Reduce Verification）**
  除实现阶段外，**前置探路（多路并行检索代码库上下文）**与**后置审查（静态工具并发 + 多维度 Review 并发）**全面并行化。所有并行分支合并后，必须在全局 Diff 上执行一次统一的结构去重与减法审查，消除各分支内部各自生成的重复局部逻辑。
