# 个人编程偏好

本文件记录用户的编程风格偏好与工作习惯，适用于**任何编程相关对话**（无论是否在工作流内）。当用户请求编写、修改或审查代码时，自动应用这些准则。

---

## 文档最小化准则（Code Over Docs）

**核心原则**：代码本身应当是最准确的文档。文档的过时速度远快于代码演进，精力应投入在编写清晰易读的代码，而非维护易过期的文档。

### 严禁生成的文档类型

* **复述代码现状的说明性文档**：
  * 目录结构说明（"src/ 包含源码，tests/ 包含测试"）
  * 类型定义罗列（把代码中的 struct/interface 再用自然语言描述一遍）
  * 接口调用说明（"调用 foo(x, y) 会返回 z"）
  * API 参考手册（把函数签名和参数类型复制粘贴到 Markdown）
  * 这类文档随代码演进会迅速过期失真，维护成本远高于价值。

* **使用示例 README**（若代码已足够自解释）：
  * 若函数签名、类型定义、测试用例已经清晰表达用法，不需要额外的 usage examples
  * 仅当面向外部用户的公共库、CLI 工具等需要快速上手指南时，才编写极简的 Getting Started

### 仅保留的文档类型

* **领域术语表（GLOSSARY.md）**：
  * 定义项目特有的领域概念、Canonical Terms
  * 相对稳定，不随代码重构频繁变动
  * 示例：`Owner`（拥有 mihomo 配置文件的系统用户）、`Generation`（一次完整的配置生成快照）

* **架构决策记录（docs/adr/）**：
  * 仅记录 **WHY**（为什么做这个决策、排除了哪些替代方案）
  * 不记录 WHAT/HOW（这些由代码本身表达）
  * 示例：`adr-001-why-use-worktree-isolation.md`（解释为什么选择 Git worktree 而非 Docker 容器隔离）

* **极简的项目入口说明**：
  * 仅在项目根目录 README 说明：项目目的、如何构建、如何运行
  * 不超过 50 行，不包含详细 API 文档

### 执行准则

* 若用户未明确要求文档，**默认不生成任何文档**
* 若用户要求"写个文档"，先反问："是需要记录架构决策（WHY）还是使用说明？代码本身是否已足够清晰？"
* 代码提交前检查：是否产生了复述代码的 docs/ 文件？若有，删除

## 注释精简准则（Comment Only the Unexpressed）

**核心原则**：代码自解释 WHAT 与 HOW，注释仅保留代码字面无法表达的信息。

### 严禁的注释类型

* **分步解说注释**：
  ```rust
  // Step 1: 初始化变量
  let mut count = 0;
  // Step 2: 遍历列表
  for item in list {
      // Step 3: 累加计数
      count += 1;
  }
  ```
  → 若代码需要这样解说才能理解，应该重构代码（提取函数、改善命名），而非添加注释

* **复述代码的文档注释**：
  ```rust
  /// 计算两个数的和
  /// 
  /// # Arguments
  /// * `a` - 第一个数
  /// * `b` - 第二个数
  /// 
  /// # Returns
  /// 返回 a + b 的结果
  fn add(a: i32, b: i32) -> i32 { a + b }
  ```
  → 函数签名已完整表达，文档注释纯属冗余

* **被注释掉的死代码**：
  ```rust
  // let old_impl = foo();  // 旧实现，保留以防万一
  let new_impl = bar();
  ```
  → 版本控制系统已保存历史，无需在代码中留墓碑

### 保留注释的三项判据

若一段注释**同时满足**以下三项，才允许保留：

1. **引入代码字面之外的信息**：
   * 外部协议限制（"HTTP RFC 规定 User-Agent 长度不超过 256 字符"）
   * 硬件/平台边界（"Linux 下 pipe buffer 默认 64KB，超过会阻塞"）
   * 反直觉实现的权衡理由（"此处用 Vec 而非 HashMap，因实测 N<10 时遍历更快"）
   * 缺陷编号或绕行说明（"Workaround for https://github.com/foo/bar/issues/123"）

2. **删掉它会破坏隐藏的不变量或前置条件**：
   ```rust
   // SAFETY: caller guarantees ptr is aligned and points to valid memory
   unsafe { ptr.read() }
   ```
   
   ```rust
   // Invariant: items 必须按 timestamp 升序排列，insert() 依赖此假设
   struct EventLog { items: Vec<Event> }
   ```

3. **能否压缩为极简的一行**：
   * 若需要多行段落才能解释，说明代码设计有问题，应该重构而非写长注释
   * 唯一例外：复杂算法的核心数学公式或协议状态机

### 执行准则

* 默认不写注释，优先通过类型签名、函数命名、代码结构自解释
* 编码完成后，逐条审查注释：
  * 是否满足三项判据？不满足则删除
  * 能否通过重构代码（提取函数、改善命名）消除注释需求？

## 范围纪律（Scope Discipline）

**核心原则**：仅编写满足当前需求的最小代码，不为未来预留扩展点。

* 严禁添加需求未要求的：
  * 配置项（"以后可能要支持配置，先留个字段"）
  * 防御性分支（"虽然上游保证不会传 null，但以防万一还是判断一下"）
  * 未被调用的辅助函数（"以后可能用到"）
  * 未请求的 UI 元素（副标题、装饰性文案、多余按钮）

* 删减判据：移除该代码/UI 元素后，当前需求契约是否依然成立？若依然成立，必须删除

## 代码清晰度优先（Clarity Over Cleverness）

* **优先使用标准库组合子**（map/filter/fold）而非手写命令式循环
* **避免过早优化**：先写清晰的代码，性能瓶颈出现后再针对性优化
* **避免单字母变量**（除循环索引 `i` 和通用约定如 `x`/`y` 坐标）
* **函数保持单一职责**：一个函数只做一件事，若需要用 `and` 描述函数职责则应拆分

## 触发时机

当用户的请求包含以下关键词或意图时，自动应用本文件准则：
* 编写代码、修改代码、审查代码
* "帮我实现..."、"修复这个 bug"、"重构..."
* 任何涉及生成或修改源代码、测试代码的场景
* 但**不包括**：编写 skill 文档、编写 ADR、编写 GLOSSARY（这些属于元文档，需要存在）
