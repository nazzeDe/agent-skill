# 静态骨架与支点锁定（Skeleton）

在不编写具体业务实现逻辑的前提下，找到改动体积最小的上游支点，并在源码中把**数据结构、类型定义与函数签名**静态锁死。

## 寻找上游支点（Upstream Lever Search）

动笔修改任何代码前，顺着数据流与调用链向上游回溯：
* **区分生产端与消费端**：问题或需求源于数据产生的入口（Boundary / Parser / Constructor），还是下游消费处？优先在数据入口做归一化或类型收紧，避免在多个下游消费点堆砌防御性 `if/else` 补丁。
* **盘点调用方契约（Caller Invariants）**：检查所有真实调用点已经保证的不变量。凡是上游契约保证不会发生的情况，严禁在签名或结构中为其预留防御性分支。
* **第一性原理审视**：假设项目今天刚创建、原本就包含此需求，最自然的数据结构与接口会长什么样？若现有结构阻碍了极简表达，直接调整该结构，而非在旧结构外打补丁。
* **对齐领域词汇**：若仓库存在 `GLOSSARY.md` 或相关 `docs/adr/`，类型名、字段名与函数名必须严格使用其中的 canonical terms。
* **完成判据**：已用一两句话明确写出“选定哪个上游位置作为修改支点，以及为什么它比改下游更省代码”。

## 落盘代码骨架（Code Skeleton）

直接在代码库中编辑源码文件，只写“骨”，不填“肉”：
* **锁死数据形状（Data Shape）**：定义或修改真实的 `struct`、`enum`、`type`、`interface` 或 Schema，利用类型系统使非法状态在编译期不可表示（Make illegal states unrepresentable）。
* **锁死接口签名（Function Signatures）**：写出新增或变更函数的完整签名（参数类型、返回类型、错误类型），函数体统一留空桩（如 Rust 的 `todo!()`、Python 的 `raise NotImplementedError`、TS 的 `throw new Error("todo")`）。
* **零衍生噪音**：不写任何未经需求要求的预留字段、配置项、辅助方法或解说式注释。
* **静态类型验证**：运行项目的编译或类型检查命令（如 `cargo check`、`tsc --noEmit`、`pyright`），确保骨架代码本身无语法与类型错误。
* **完成判据**：源码中的类型与空签名已通过编译/类型检查，且未包含具体业务实现逻辑。

## 输出交接摘要

向调用方返回结构化摘要：
* **支点声明**：一两句话说明选定的根因支点与被排除的下游补丁方案。
* **骨架 Diff**：展示新增/修改的类型与函数签名（`git diff`）。
* **并行切分判定**：列出待填充的函数签名清单，明确它们属于**单一内聚模块**（单 Worker 执行），还是**彼此无状态共享的正交模块**（可在 `work` 阶段由多个并行 Worker 独立填肉）。
* **完成判据**：摘要包含支点声明、通过类型检查的骨架 Diff 以及明确的并行切分判定。
