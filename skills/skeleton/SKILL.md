# 静态类型与接口签名定义（Skeleton）

在不编写具体业务实现逻辑的前提下，定位改动体积最小的上游修改点（Upstream Modification Point），并在源码中将**数据结构、类型定义与函数签名**静态锁定。

## 定位上游修改点（Upstream Root-Cause Analysis）

动笔修改任何代码前，顺着数据流与调用链向上游回溯：
* **区分生产端与消费端**：问题或需求源于数据产生的入口（Boundary / Parser / Constructor），还是下游消费处？优先在数据入口做归一化或类型收紧，避免在多个下游消费点重复添加防御性 `if/else` 分支。
* **核对调用方不变量（Caller Invariants）**：检查所有真实调用点已经保证的前置条件与不变量。凡是上游契约已保证不会发生的状态，严禁在签名或数据结构中为其预留防御性分支。
* **第一性原理审视（First-Principles Design）**：假设项目今天刚创建、原本就包含此需求，最直接的数据结构与接口应当如何定义？若现有结构阻碍了简洁表达，直接重构该数据结构，而非在旧结构外层叠加适配代码。
* **对齐领域词汇**：若仓库存在 `GLOSSARY.md` 或相关 `docs/adr/`，类型名、字段名与函数名必须严格使用其中的 canonical terms。
* **完成判据**：已用一两句话明确说明“选定哪个上游位置作为修改点，以及为什么它比在下游修改产生更少的代码”。

## 定义类型与函数签名（Types & Function Signatures）

直接在代码库中编辑源码文件，仅编写类型定义与函数签名，不编写具体实现逻辑：
* **锁定数据形状（Data Shape）**：定义或修改真实的 `struct`、`enum`、`type`、`interface` 或 Schema，利用类型系统使非法状态在编译期不可表示（Make illegal states unrepresentable）。
* **锁定接口签名（Function Signatures）**：写出新增或变更函数的完整签名（参数类型、返回类型、错误类型），函数体统一留空桩（Stub，如 Rust 的 `todo!()`、Python 的 `raise NotImplementedError`、TS 的 `throw new Error("todo")`）。
* **范围纪律（Scope Discipline）**：不写任何未经需求要求的预留字段、配置项、辅助方法或解说式注释。
* **静态类型验证**：运行项目的编译或类型检查命令（如 `cargo check`、`tsc --noEmit`、`pyright`），确保类型与函数签名无语法与类型错误。
* **完成判据**：源码中的类型与空函数签名已通过编译/类型检查，且未包含具体业务实现逻辑。

## 输出交接摘要

向调用方返回结构化摘要：
* **上游修改点声明**：一两句话说明选定的根因修改位置与被排除的下游局部修改方案。
* **签名 Diff**：展示新增/修改的类型与函数签名（`git diff`）。
* **并行切分判定**：列出待实现的函数签名清单，明确它们属于**单一内聚模块**（单 Worker 执行），还是**彼此无状态共享的正交模块**（可在 `work` 阶段由多个并行 Worker 独立实现）。
* **完成判据**：摘要包含上游修改点声明、通过类型检查的签名 Diff 以及明确的并行切分判定。
